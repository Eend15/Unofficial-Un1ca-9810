# Frosted card material

The expanded island defaults to Classic. Appearance → Card material can opt into Frosted glass at runtime; absent or invalid preference values select Classic. Existing explicit selections are preserved. `material_style` is an integer: 0 for Frosted glass, 1 for Classic. This preference is independent of custom corner radius, accent, glow and animation settings.

Only the card shell changes. Existing Lottie icons, button shapes/colours, content layout, typography, input handling, content blur and compact black pill remain in their existing rendering paths. Classic retains the former native SemBlur backdrop, fill, rim and overlaid media glow. Low-performance mode retains its opaque background policy.

## Live background

`MaterialCapture` runs inside SystemUI and uses the hidden `IWindowManager.captureDisplay` / `ScreenCapture.CaptureArgs` APIs. Every request excludes an owned, verified copy of the island window's SurfaceControl, including all its children, so the painted island cannot feed back into its own material. Requests are cropped to the target stack plus filtering margin, downsampled to at most 420 px wide, and bounded to 10 Hz. Capture/readback/filtering run on a single worker; music motion and foreground continue at the display frame rate. Identical pixels reuse the filtered texture.

Dev2–dev4 used Samsung's `takeScreenshotToTargetWindow` service method when present. It passes the verified host root's system-window type, `containsTarget=false`, `useIdentityTransform=false` and `ignorePolicy=false`. Samsung's server selects the window below the target system window, so the client does not need any `ScreenCapture.CaptureArgs` class. This remains a firmware fallback from dev5. It never requests an unrestricted full screenshot that could feed the island back into itself.

On other vendors it derives the argument, builder and listener classes from the actual device window-service signature using the SystemUI host loader. It does not resolve a fixed `android.window.ScreenCapture$CaptureArgs` name through the LSPosed module loader. The supplied One UI 9 / SDK 37 report showed that lookup failing in dev1 before any frame could reach the shader. Fixtures exercise both Samsung's below-window/policy flags and a host-only/renamed AOSP argument/listener API.

The live-activity and music cards in the notification shade also use this material. `ShadeMaterialBackdrop` shares one capture/filter worker per shade window, excludes that whole window, and maps each row's local coordinates to its screen region. Only a successfully painted material suppresses the old native row background; the last departing owner restores its alpha/outline behaviour. Stopping the style, hiding a row and detaching the window release clients and stop unused work. Static cards request frames through 90 ms blends of arriving backdrop pixels. Waiting on the opaque local material alone does not keep a frame loop running.

The worker publishes immutable texture/coordinates to the UI thread. Captured pixels remain in memory and are never written to disk. Secure content is not requested. Stale surface/display epochs are discarded, display-size changes drop the old frame, and hidden/detached/classic/low-performance states stop requests and release cached references. GPU-bound bitmaps are never recycled while a display list might reference them. Reduce-transparency accessibility settings also stop the custom backdrop.

This is a privileged, vendor-dependent path: the API can fail or be denied on a particular firmware. Reflection/readback/shader failures retain the native or opaque fallback and appear in diagnostics as `card material backdrop` / `card material`. Successful shader recording is not proof that a particular phone permits compositor capture. Device appearance and capture permissions require phone validation.

## Approved material

`MaterialPixels` ports the supplied-background review's floating-point down/up filtering, with antialiased bilinear resizing. Down taps are `(4 * centre + four diagonals) / 8`; up taps are `(four diagonals + four axial samples at offset 2) / 8`. The .75 radius is normalized to the review's 1164 px screen width, rather than using the same pixel radius on every display. Float intermediates avoid repeated eight-bit quantization. Foreground content never passes through this filter.

`frosted.agsl` is the runtime source of truth. It applies luminosity and colour-dodge mixing, the approved black-to-translucent material, G2/lp geometry with weight 2.4, and the approved curved lighting. Default geometry scales the reference radius 100 to the card width 1072; a user's existing custom radius overrides it. Classic keeps its original 28 dp default.

Gradle compiles this exact asset into `FrostedShaderSource.CODE` in dex. The SystemUI runtime does not open a Java resource through the module classloader: LSPosed's in-memory dex loading must not make the shader disappear. The native-graphics test checks that the generated constant equals the source asset byte-for-byte as text before recording its bindings.

The visible panel perimeter is evaluated by the shader, not painted as an ordinary circular round-rect with a new rim on top. Foreground clipping uses `MaterialShape`, a 48-segment-per-corner sampling of the same lp/G2 contour. It changes the panel boundary, not the designs of the icons and controls inside it.

The COUI lighting functions come from the supplied ColorOS SystemUI study (`com.coui.appcompat.shadowedge.agsl.ShadowEdge`). The entry point is renamed to `couiLight`. Dev5 also replaces three descending `smoothstep` calls with the explicit same Hermite polynomial, because reversed edges are undefined in GLSL; other lighting equations are retained, with the same style-2 mapper and explicit .6/.3 strength selected in the approved preview. These strengths and the fitted material coefficients are visual choices, not a claim that the screenshot's private runtime preset was recovered. No ColorOS APK, framework classes, Compose dependency or native binary is bundled.

The rejected whole-surface brightness compression is **not** applied. Continuous local linear-luminance/variance statistics modulate a soft inner roll and the existing curved glint. The edge correction tapers to exactly zero 64 reference pixels inward; it does not change the radius or select discrete bright/dark presets. The packed 16-bit response map is bound as data with `RuntimeShader.setInputBuffer`, avoiding colour-space transformations.

Dev3 responds continuously to ordinary bright wallpaper with a normalized shoulder `(1 + .22²) * E² / (E² + .22²)`, weighted by local uniformity. Near-black apps retain virtually the same response. Brightness correction lifts only the upper opaque cap by at most .18 times this response with a smooth vertical fade; lower-glass transmission stays unchanged. A luminance-preserving 32% maximum desaturation softens dirty wallpaper/icon casts before album colours are mixed. Album palette hues are not desaturated. This reduces the black-band appearance in the provided bright-wallpaper screenshot without dimming the whole material.

Dev4 addresses the remaining split shown by the maintainer's phone screenshots. Card-wide exposure now carries 80% of the exposure estimate, with 20% local influence, and textured wallpaper retains at least 85% of the exposure response. This prevents a bright launcher icon from imposing a different material response on one side of the card. All weights remain continuous. On luminous backdrops, `R * (2 - R)` blends non-music opacity toward a shallow .72 → .60 profile with a neutral charcoal tint. This redistributes transmission from the lower body into the formerly black cap; it is not a global darkening multiplier. Background-only desaturation rises to 90% at full response, before any album colour is applied. The album material retains its former vertical opacity profile, while the dark-screen response remains negligible. The original G2 shape and COUI curved lighting functions remain unchanged.

## Dev5 render parity

The dev4 phone report confirms the new GPU material is actually running; it is not the Classic fallback. Native Android/Skia review with the production `FrostedSurface` bindings reproduces the previous Python material on uniform inputs. For the supplied pink screenshot, the phone still has a darker upper body than either controlled render; this difference has not been proven to be a colour-coefficient defect.

`DisplayCaptureApi` now prefers the device window service's explicit `setExcludeLayers` path even on Samsung. It resolves arguments/listeners from the actual service signature with the host loader, avoiding the dev1 fixed-class-name error. The verified, owned host SurfaceControl and its children are excluded by identity. The old Samsung window-type selection is used only if this binding is absent or fails at runtime. Its type-based selection cannot establish the identity of a particular window when types are shared, so it is no longer the first choice for render-parity work. Both routes keep their existing protection flags. API selection, fallback and material geometry/response range are reported in diagnostics; no background bitmap is saved by the app.

`FrostedMaterialRenderTest` is an opt-in visual-review category, excluded from the ordinary test suite. It uses the generated Android shader constant, actual production uniform bindings, the 420 px cropped/filtering path, the real `BatteryBody`, and the same radius policy. The Java software-rendering guard is bypassed **only inside this review fixture** to let native Skia raster evaluate the already-bound shader. These are native Android/Skia CPU renders, not captures from the Samsung GPU. They replace illustrative Python buttons/layouts for comparison. The runtime and review share the same material source and coefficients; dev5 adds no new bright-background colour/opacity tuning.

Run the visual capture with `./gradlew -Prender testReleaseUnitTest --tests '*FrostedMaterialRenderTest'`. Optional `MATERIAL_REVIEW_INPUTS` points to a directory containing `photo.png`, `apple.png`, and `busy.png`. Outputs are in `app/build/render/material/`. Full device parity still requires phone confirmation, especially when the firmware falls back to window-type capture.

## Dev11 notification-shade perimeter

The shade screenshot showed the short live card's corners intersecting another outline. Disabling `clipToOutline` on the row alone does not remove Samsung's explicit child `Canvas.clipPath`: the Samsung `ExpandableOutlineView` reference calls `getCustomClipPath(child)` and falls back to its circular `getClipPath(false)`. A scoped hook now supplies the same native path's rectangular bounds for content that actually contains a Frosted card. The renderer remains responsible for its G2 perimeter; the stock swipe bounds, content-height clip bounds, list clipping, ordinary notification rows and notification menus are retained.

A pre-draw lease prepares the row, content ancestors and player's own outline before their first recorded frame, and hides the player's old background as well as the native row shell. Unchanged outline flags are not repeatedly written, avoiding an invalidation loop. Classic, low-performance mode, GPU failure, detach and the last owner leaving restore the stock state. Custom RemoteViews content is clipped to its own matching material perimeter. The native-graphics regression covers the formerly cut corner, retained rectangular limits, first-frame preparation and restoration. Actual One UI 9 phone confirmation is still required.

## Dev6 transmission correction

The dev4/dev5 bright-background compensation was too neutral and opaque: ordinary bright cards approached a 72% → 60% scrim, a raised charcoal tint, and 90% luminance-preserving desaturation. This could itself produce the flat grey panel rejected in the device screenshots; it is not evidence that Samsung prevents blur-radius changes. The custom Frosted path filters the captured bitmap itself and suppresses the native SemBlur layer while it paints successfully. On a uniform backdrop, the filter preserves the colour, so changing blur radius cannot fix a transmission/colour-mixing defect.

Dev6 reduces ordinary bright-card opacity targets to 60% → 46%, desaturation to 28%, and the neutral tint to (.025, .027, .035). These targets still blend continuously through the existing exposure response, with no brightness buckets. The filtering kernel/radius, source capture, G2 perimeter and COUI curved lighting are unchanged. A nonzero album `paletteAmount` keeps the existing music material coefficients, including its paused state, so this correction does not retune music. Near-black cards have negligible exposure response and keep their approved dark appearance.

The comparison is exported by `FrostedMaterialRenderTest`, using the app's actual shader bindings, background filtering and BatteryBody. Actual phone appearance still needs confirmation; the fixture is native Android/Skia raster, not a Samsung GPU screenshot.

## Dev7 transition continuity and music colour

The supplied 16.6 s recording showed the media material becoming nearly black before the card had folded, then gaining its material late on opening. Two fades were multiplied: the custom material used the native SemBlur early-removal curve and also had a separate 180 ms first-capture entry fade. `StackPainter` now drives custom material solely from the morph geometry, reaching full material at 65% expansion and retaining it through the middle of the fold. The native-only early blur removal and Classic appearance remain independent.

`FrostedSurface` can paint the same G2 shell, curved lighting and album colour immediately against a local opaque 1px black input while compositor pixels are prepared. Only captured background input/response blends in over 90 ms; lighting and album colour do not restart. Dev7 switched back to native/opaque rendering after a 500 ms wait; dev8 removes this mode switch because a late capture could switch the surface again. GPU failures still use the Classic fallback. A new focused native-graphics test verifies the pre-capture light, identical output at the instant pixels first arrive, gradual pixel blending, and fallback after a failed capture.

The capture region grows through spring overshoot instead of shrinking/changing generation on each geometry update. In-flight captures of the smaller region remain usable; both texture and response sampling clamp at a crop edge until the next larger capture. Surface/display changes and hidden/detached states still invalidate pending work.

The maintainer additionally identified the **music card's album colours** as dull. Only the music material gets a 1.25 chroma expansion about its existing RGB luminance, limited to the RGB gamut. It happens before curved white lighting and preserves the album hue family; it does not add an overlaid glow, alter foreground icons/buttons, retune ordinary cards or increase the music material's luminance. The original extracted palette and moving weight fields remain the source.

## Dev8 capture flicker correction

The follow-up 11.68 s phone recording exposed flickering with dev7. Its 500 ms local-material timeout could select the native/Classic surface mid-transition, then return to Frosted when a late capture arrived. Newly arriving captures after the first one also replaced textures immediately, and a null frame hard-cleared the surface. The material now stays on one GPU renderer throughout an opening/fold; a missing capture uses its opaque local material, with no timed renderer switch. GPU compilation/binding errors still disable the custom renderer and restore Classic.

Each accepted capture has an input bundle containing its texture, response field and coordinate mapping. The previous and current bundles blend together over 90 ms at display cadence. Both maps follow the current morph geometry, so changing the crop cannot misalign the old and new background. If another capture arrives mid-blend, the active blend finishes before adopting the latest scene frame. No blend starts from black after an established capture. Static cards explicitly request another frame when a blend starts during painting, after the earlier motion check.

`MaterialCapture` tolerates short null/readback-root gaps for 200 ms before reporting a sustained loss. A `FrostedSurface` also retains a valid input for a short gap, then blends to its local opaque input rather than changing renderers. Input loss no longer clears shader, phase and geometry. Hidden/detached windows still hard-clear cached material. These are transient in-memory images; no screen data is saved by the app.

The focused native pixel test now checks late capture past 500 ms, missing-frame hold, subsequent capture interpolation from the previous colour, and smooth sustained-loss fallback. The ordinary settled material and the music chroma enhancement remain the dev7 values.

## Prewarming before expansion (dev10)

The next phone recording showed ordinary notification cards changing from the local black input to the real backdrop after expansion had already begun. Interpolation alone cannot remove the delay of starting the first capture only once a card exists. Frosted now primes a full-display, 420px-wide backdrop while the compact island is visible, at 1 Hz. Touch-down requests a refresh. Expansion switches to the actual stack crop at the existing 10 Hz maximum; in-flight warm pixels remain usable, and the envelope is not kept full-screen for expanded captures. A surface created with a prewarmed frame uses it immediately, rather than starting another artificial black fade. Hidden, paused, shade-obscured, low-performance and Classic states do not prewarm. The focused test verifies capture eligibility while compact and immediate use of an available frame; real phone confirmation is still needed.

## Music

The music shell uses `MediaFx.waveformColorAt(0 / .5 / 1)` and therefore the same artwork palette and smooth track-change transition as its waveform. Three material-colour weight fields travel across the card over a ten-second cycle. They are mixed into the material before lighting, rather than drawn as additional glow layers. The lower tint and 1.2% breathing match the approved visible-flow preview at the default motion strength. Playback liveness smoothly reduces colour/motion while paused. The existing glow colour selection and motion setting remain available. The classic media background is skipped only when the new shell actually paints successfully.

The new shader blends toward black through the open/fold geometry and blends in its first valid backdrop pixels; native backdrop alpha remains independently controlled. Input/content continuity and the foreground blur transition remain with `StackPainter` and `ContentBlur`.

## Validation

- Android native-graphics test records the packaged shader and all uniforms/texture bindings on a hardware RecordingCanvas, and checks the Classic opt-out.
- Float filtering was compared with the review renderer on the same 420 × 640 input: mean error 0.0084 and maximum 0.0528 of an eight-bit channel level.
- The runtime material shader was compared in Skia raster with the approved review on white, black and ivory: mean RGB error approximately 0.55, 99th percentile 2, maximum 3 channel levels, including edge antialiasing and dithering. Source provenance is preserved; dev5 makes only the documented descending-ramp compatibility substitutions in that COUI prefix. This is a formula/render comparison, not a Samsung device screenshot.
- The ordinary test suite checks settings persistence, shared foreground rendering and filtering. Existing fixed-28-dp regression captures explicitly select Classic; new-material checks are kept focused.

The maintainer's dev2 screenshots confirm the desired dark-background appearance on the phone. The dev3 screenshots still showed an excessive dark-cap/light-bottom split and yellow wallpaper casts. The dev4 report and screenshots confirm that its material path runs, but its bright-background appearance is still rejected. Dev5 capture/ramp changes need phone confirmation. Rendering comparisons are labelled script renders and do not substitute for that confirmation.
