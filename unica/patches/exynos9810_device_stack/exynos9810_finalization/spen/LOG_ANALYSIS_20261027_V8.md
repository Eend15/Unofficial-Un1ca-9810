## What the briefing establishes and what remains a hypothesis
Official android16-release LeScanningReassembler::ProcessAdvertisingReport caches a scannable advertisement until scan response unless ignore_scan_responses is true. The source even documents that waiting can fail when advertisers reject scan requests. The actual ROM libbluetooth_jni.so contains the same wait-for-scan-response and full-report strings. Both private HCI captures have connectable Crown ADV_IND reports and no scan responses for that address (795 reports in073443,104 in131122). This is strong evidence consistent with the proposed GD boundary; it is not a runtime proof that this exact branch is the sole cause in Samsung's compiled stack.
Source: https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/android16-release/system/gd/hci/le_scanning_reassembler.cc

Opportunistic mode shares other clients' scans; it is not a guaranteed passive radio scan. Current Android docs expose setScanType(PASSIVE) from36.1, but the actual ROM framework-bluetooth.jar extracted read-only from com.android.bt.apex has no setScanType/getScanType API. Do not invent reflection members or silently use opportunistic mode as the same mechanism.

## Implementation
AirCommand candidate is based on the installed v6 decoded source (not v7 software-filter trial). L2/m's existing advertisement runnable first asks L2/p.unicaTryKnownCrownGatt. That helper checks cancellation/current epoch/deadline, Note9 N960F/N960N bootloader, built-in pen profile, nonempty valid stored address, BLE adapter availability and an actual getRemoteDevice result. It records its attempt epoch and retires the pending advertisement operation, then calls the existing L2/p.c driver-open path. That original path performs real transport-LE GATT connection, service discovery, Crown profile validation and normal callbacks/retries. No new success code, synthetic ScanResult, fake BluetoothDevice, fixed MAC or binding-data reset is introduced. It tries at most once per original connection epoch; remaining retries and unknown/invalid-address cases use original discovery. An unknown pen with no saved address is NOT fixed by this route.

The app-local Notes engine uses the same pinned8-byte JNI capability fallback as v7, leaving the accepted v6 recognizer, APK signatures and note data unchanged. Both are still physical test candidates. The renderer trial is supported by a verified existing Java fallback, not a claim that the hypothesized AOD refresh cause is proven.
